# my-skills-czf : doc-CV-description

## 事实核验

1. 先读取用户提供的代码、文档、变更记录或数据，提取目标、约束、关键文件、技术决策和验证证据。
2. 区分已实现、已验证、计划优化和推测内容。没有证据的线上指标、性能结果、用户反馈和个人贡献不得写成事实。
3. 对缺失的关键信息明确标注“当前未提供”，并说明需要怎样的测试、日志或数据才能验证。

## 固定结构

除非用户指定其他结构，按以下顺序输出；缺少内容时说明原因，不保留空标题。

### 1. 简历写法

概括“负责什么、解决什么问题、采用什么关键技术、已确认的结果，结果最好是可以量化的，若不推荐量化，则用括号说明”。随后用不超过三条的项目符号列出关键职责或技术动作。突出个人职责，不把团队工作全部写成个人贡献。注意是简历写法，不应该堆砌过多字数，字数不宜超过100字。

### 2. 面试表达主线

这部分你将扮演一名专业软件工程师的角色，当你在解决这个需求的时候，你是如何一步步排查该问题或者解决这个需求的，顺序可以是：业务背景、一开始的思路、实际上手解决后发现了什么、发现问题、思考方案解决问题、方案选择、风险判断、验证机制、并给出选择该方案对应的合理的解释。全过程应该的语言表述应该符合一名优秀工程师的角色，应该是有逻辑、有体现自主思考的。全程不堆砌 API 名称。因为这个过程更注重解决问题的思路以及工程思维，面试官可能并不在乎你的代码怎么写。


### 3. 方案选择

这部分用表格比较两个到三个真实可行方案，列为“方案、优点、局限、结论”。比较必须围绕实际约束，例如动态布局、性能、交互、兼容性、维护成本、数据一致性或项目既有架构。表格后用一段话说明最终选择和原因。

### 4. 实际实现

按数据流或生命周期从入口到清理展开。为每个有两个以上分支的主题创建三级标题，例如“点击与请求保护”“状态更新”“并发控制”“销毁收口”。

- 每个小节先说明文件和方法，再说明输入、关键判断、状态变化、副作用和下一跳。
- 顺序性逻辑使用有序列表，例如“入口 -> 请求 -> 回包 -> Store -> 视图 -> 清理”。
- 协议字段、状态字段和方法名使用行内代码。
- 涉及并发时，明确请求 ID、版本号、去重键、定时器句柄、取消条件和过期动作。
- 引用真实文件和行号时，行号必须来自当前代码检查结果；未找到视图调用处时直接说明。

### 5. 已确认结果与验证缺口

优先使用三列表格：“分类、已从代码或测试确认、当前未提供”。将用户可观察行为、自动化测试、线上指标分开陈述。没有执行测试时不得写“验证通过”。


### 6. 高频追问与回答要点

这部分要求你扮演中国各大互联网大厂面试官的角色，对面试者的描述提出疑问，要求体现技术深度以及设计和架构思维。
每个问题使用三级标题，下一段给出体现工程思维、逻辑思维的回答，不能过于语义化，应该符合正常人的表达习惯。优先覆盖：方案取舍、关键机制、乱序与重复事件、边界场景、性能、生命周期与内存安全、验证方法和指标缺口。

## 排版规则

- 使用一个一级标题作为文档标题，固定结构使用二级标题，只有存在两个以上独立分支时才使用三级标题；不要使用四级及更深标题。
- 每段只表达一个中心结论，优先控制在两到四句；超过四句时拆成小节、列表或表格。
- 同类规则、步骤、字段和风险使用列表；方案、状态对照、验证缺口和复盘使用表格。表格控制在三到四列，避免把长段落塞进单元格。
- 使用引用块强调唯一的核心判断，不连续堆叠引用块；使用加粗突出关键结论，使用行内代码突出字段、方法、状态和配置。
- 技术实现章节必须可顺着阅读成完整链路，不能只罗列文件名；表达风格应适合直接口述。
- 写入知识库文档时保留已有文档标题和无关内容，优先局部更新目标章节；完成编辑后发布并回读关键标题、列表和表格。

## 输出约束

- 使用中文和清晰的小标题。
- 只总结真实输入中的事实，可适当虚构性能数字、线上结果、用户反馈或职责。
- 同时保留“选择了什么”和“为什么选择”，并让结果能够回指到实现动作或验证记录。
- 用户明确要求纯口述稿、简历一段话或其他格式时，按用户格式输出，不强制完整八层结构。
