# 增量模式工作流

> 当用户提供了已有方案文档，或说"补充接口设计"、"完善缓存设计"时，使用本流程。

## 流程概览

```
Step I-1 (分析)     → 分析已有方案，识别缺失章节
Step I-2 (确认)     → 确认补充范围
Step I-3 (探索)     → 探索代码库（聚焦待补充章节）
Step I-4 (patch)    → 生成补充内容
  ⏸ 用户确认补充内容（必须，可循环调整）
Step I-5 (tasks)    → tasks.md（仅针对新增部分）
  ⏸ 用户确认 tasks.md（必须，可循环调整）
Step I-6 (后续)     → 执行实现 + changes.md + summary.md
```

---

## Step I-1：分析已有方案

### 输入方式

用户可通过以下方式提供已有方案：
1. **文件路径**：`请基于 /path/to/spec.md 补充接口设计`
2. **粘贴内容**：直接粘贴方案文档内容
3. **工作区文件**：`请基于当前打开的文件补充缓存设计`

### 分析步骤

1. 读取文档内容
2. 按 `references/doc-template.md` 的标准章节结构（§1 ~ §9）逐一检查
3. 识别：完全缺失、内容为空、内容不符合规范的章节
4. 输出分析报告（章节完整性表格 + 待补充章节列表），询问用户确认

---

## Step I-2：确认补充范围

向用户展示分析报告后，确认补充范围。支持的粒度：

- **单章节**：`只补充 §6.4 接口设计`
- **多章节**：`补充 §6.3 和 §6.4`
- **全部缺失**：`补充所有缺失章节`

---

## Step I-3：探索代码库

聚焦与待补充章节相关的代码进行探索。探索策略：

- 补充 §6.4 接口设计 → 探索现有接口定义、路由配置
- 补充 §6.2 缓存设计 → 探索现有缓存使用方式
- 补充 §6.3 关键技术 → 探索现有技术选型和配置

**工具选择**：

| 场景 | 推荐工具 |
|------|---------|
| 读已知路径的文件 | `read_file` |
| 搜索函数名、常量、接口路径 | `grep_content` |
| 按文件名模式查找 | `glob_path` |
| 理解某段逻辑属于哪个模块 | `delegate_subtask(Explore)` |

**多模块场景**：当待补充章节涉及多个独立模块时，必须通过 `delegate_subtask(agent_type=Explore)` 将各模块探索委托给独立子 Agent 并行执行，在**同一条消息中**发起多个调用。子 Agent 查询只包含与需求相关的 2-4 个信息段，禁止要求返回完整代码。

**查询模板**：

```
请探索 [模块名称/目录路径]，聚焦与 [需求关键词] 相关的部分，按以下格式返回：

## 模块概述
- 职责：[一句话]
- 技术栈：[框架、存储、中间件]

[从需求中选取 2-4 个信息段拼接在此]

注意：只返回与 [需求关键词] 直接相关的内容，无关的表/接口/文件不要列出。
```

**项目级规约检查**：同时检查项目根目录下是否存在 `.comate/rules/` 目录，若存在则读取相关规约文件。

---

## Step I-4：生成补充内容

读取 `references/patch-template.md` 作为骨架，遵循对应规范文件，保持与已有章节一致的写作风格。

**规范文件按需加载**：
- 补充 §6.2 数据库部分 → 读取 `references/database-design-standard.md`
- 补充 §6.2 缓存部分 → 读取 `references/cache-design-standard.md`
- 补充 §6.4 接口部分 → 读取 `references/api-design-standard.md`

**输出方式**：
- 若用户提供的是工作区文件路径：用 `edit_file` 直接插入原文档
- 否则：用 `write_file` 写入 `.comate/specs/{feature_name}/patch.md` 并附插入说明

### 用户确认（强制）

补充内容写入后，**必须立即停止执行，不得进入 Step I-5**。向用户输出确认请求：

```
补充内容已生成，请 review。确认后将继续生成任务拆分（tasks.md）。如需调整，请直接说明修改要求。
```

- **等待用户明确同意** → 进入 Step I-5
- **用户要求调整** → 修改后**再次请求确认**，循环直到用户确认
- **绝对禁止**在未收到用户同意的情况下自动进入下一步

---

## Step I-5：生成 tasks.md

读取 `references/tasks-template.md` 作为骨架，仅生成与补充章节相关的实现任务。

**任务拆分规则**：
- **数据层**：DDL 执行、数据访问逻辑、缓存逻辑 → 分别独立任务
- **业务层**：按架构图中的模块拆分
- **接口层**：按接口数量拆分（多接口可合并）
- **路径精确**：所有路径占位符必须替换为 Step I-3 探索到的实际文件路径
- **验证类任务**：标记 `⚠️ 人工确认`，不自动标记完成

### 用户确认（强制）

tasks.md 写入后，**必须立即停止执行**。向用户输出确认请求：

```
tasks.md 已生成，请 review：.comate/specs/{feature_name}/tasks.md
确认后将开始按任务执行代码实现。如需调整，请直接说明修改要求。
```

- **等待用户明确同意** → 进入 Step I-6
- **用户要求调整** → 修改后**再次请求确认**
- **绝对禁止**在未收到用户同意的情况下自动进入 Step I-6

---

## Step I-6：后续阶段

### 执行代码实现

1. 按 tasks.md 中的任务顺序执行
2. 每完成一个 Task，立即更新 tasks.md 中对应的 `[ ]` → `[x]`
3. **验证类任务**（标记 `⚠️ 人工确认`）不自动标记完成，等待用户确认
4. 代码实现必须符合方案中的设计

### 生成 changes.md

读取 `references/changes-template.md` 作为骨架，记录代码实现过程中所有文件变更（新增/修改/删除）。写入 `.comate/specs/{feature_name}/changes.md`。

### 生成 summary.md

读取 `references/summary-template.md` 作为骨架，汇总任务执行状态、变更统计、规范检查结果和待办事项。写入 `.comate/specs/{feature_name}/summary.md`。

> 任务和变更范围仅覆盖本次新增部分。
