# API 设计通用规范

> 本文件为通用规范，项目级规约（scenarios/api-design.mdr）优先级更高，两者同时加载时以项目级为准。
> 来源：TSC-API 治理 / 后端应用 Web 服务 API 开发与使用规范

## 1. 适用范围

本规范适用于 RESTful、GraphQL、Socket/WebSocket、SSE、RPC 等通过 Web 形式对外提供的 API。

## 2. API 管理要求

- **[强制]** 接口文档必须包含必要内容，符合本规范
- **[强制]** 接口实现代码包含必要的注解或注释
- **[强制]** 接口文档托管在 API 管理平台（推荐 iAPI 平台）
- **[强制]** 接口实现代码托管在 iCode 平台

## 3. 接口文档规范

### 3.1 接口名称
- **[强制]** 包含中文，能体现接口的功能或用途，不能出现错别字

### 3.2 接口描述
- **[强制]** 包含中文描述，清晰说明用途、行为和预期结果
- **[强制]** 如接口在安全性、版本兼容性、幂等性等方面有特殊约束，需在描述中说明

### 3.3 请求方法
- **[强制]** 明确标注 GET / POST / PUT / PATCH / DELETE

### 3.4 请求路径

- **[强制]** 路径只能包含字母、数字、中划线、下划线、点、逗号和花括号
- **[强制]** 多级路径以单正斜杠分割，不包含重复斜杠
- **[推荐]** 路径不以正斜杠结尾
- **[推荐]** 每级路径单词首字母小写，多个单词用下划线分割
- **[推荐]** 资源名使用复数形式
- **[推荐]** 路径嵌套不超过 3 级子资源
- **[推荐]** 路径中不包含 get / delete / put 等动词（HTTP 方法已表达）
- **[强制]** 路径参数必须在请求参数中定义，且位置为 path 的参数需在路径中使用

### 3.5 请求参数

每个参数必须包含：

| 字段 | 说明 |
|-----|------|
| 参数位置 | Path / Query / Header / Body |
| 参数名称 | 清晰表意，无重复 |
| 类型 | String / Integer / Float / Boolean / Enum / Array |
| 是否必填 | 明确标注 |
| 描述 | 简要说明，有默认值时标明 |
| 示例值 | 推荐提供，符合参数类型 |

- **[强制]** 枚举类型需穷举所有枚举值
- **[推荐]** Header 参数使用连字符 Pascal 大小写（如 `Content-Type`）
- **[推荐]** 建议在请求或响应 Header 中添加请求 ID（如 `X-Request-Id`）

### 3.6 响应参数

- **[强制]** 使用标准 HTTP 状态码，至少定义一个 2xx 或 3xx 响应
- **[强制]** 同一团队的接口采用统一响应格式

**推荐统一响应格式：**

```json
{
  "code": "200",
  "message": "请求成功",
  "data": {
    "page": 1,
    "size": 10,
    "total": 50,
    "items": [
      {
        "id": 1,
        "name": "示例"
      }
    ]
  }
}
```

- **[推荐]** 尽可能描述所有可能的响应状态码和对应响应体
- **[推荐]** 响应包含示例值，且示例值与字段类型一致

### 3.7 错误码设计

错误码定义格式：

| 错误码 | 错误信息 | 触发场景 | 处理建议 |
|-------|---------|---------|---------|
| 400 | 参数错误 | 请求参数不合法 | 检查参数格式和必填项 |
| 401 | 未授权 | 鉴权失败或 Token 过期 | 重新登录或刷新 Token |
| 403 | 禁止访问 | 无权限操作 | 检查权限配置 |
| 404 | 资源不存在 | 请求资源未找到 | 确认资源 ID 是否正确 |
| 500 | 服务器错误 | 内部异常 | 联系服务端排查 |

### 3.8 鉴权方式
- **[推荐]** 鉴权方式采用具备一次有效性或短时有效性的身份凭据（UUAP、UGate、API Keys 等）
- **[强制]** 核心操作、高敏数据接口必须具备鉴权控制

### 3.9 数据安全
- **[强制]** 路径参数不能包含凭据（API 密钥、密码等）
- **[强制]** 涉及用户敏感信息不得明文传输，需加密处理
- **[推荐]** 对外公开 ID 使用难以预测的随机值

## 4. 代码注释规范（以 Go 为例，其他语言参照同等规范）

```go

// @Param body body CreateResourceRequest true "请求体"
// @Success 200 {object} CommonResponse[CreateResourceResponse] "成功"
// @Failure 400 {object} CommonResponse[any] "参数错误"
func CreateResource(ctx *gin.Context) {
    // ...
}
```

## 5. 接口设计检查清单

在技术方案的接口设计章节中，确认以下要点：

- [ ] 路径符合 RESTful 规范（小写、下划线、复数、≤3 级）？
- [ ] 每个参数标注了位置和必填项？
- [ ] 响应使用统一格式（code/message/data）？
- [ ] 定义了错误码和对应处理建议？
- [ ] 说明了幂等性？
- [ ] 鉴权方式明确？
- [ ] 是否遵守了项目级规约（若已加载）？
