## 工作流程概览

### 完整模式

```
Step 1 (收集)       → 需求理解与信息收集
Step 2 (探索)       → 探索代码库
Step 3 (doc)        → doc.md（最终技术方案文档）
  ⏸ 用户确认 doc.md（必须，可循环调整）
Step 4 (tasks)      → tasks.md（代码实现任务）
  ⏸ 用户确认 tasks.md（必须，可循环调整）
Step 5 (implement)  → 执行代码实现
Step 6 (changes)    → changes.md（代码变更记录）
Step 7 (summary)    → summary.md（完整任务汇总）
```

### 文档模式

```
Step 1 (收集)       → 需求理解与信息收集
Step 2 (探索)       → 探索代码库
Step 3 (doc)        → doc.md — 直接结束（跳过确认）
```

## 用户确认机制

**核心规则**：doc.md 和 tasks.md 生成后，必须强制用户确认才能继续后续流程。

### 确认流程

1. **doc.md 确认**（Step 3 完成后）：
   - 将 doc.md 写入磁盘后，立即**停止执行**，向用户展示确认请求
   - 等待用户回复，此时**不得自动进入下一步**
   - 若用户回复"确认"、"继续"、"ok"、"没问题"等同意指令 → 进入下一步
   - 若用户要求调整（如"修改 XX 部分"、"补充 YY 内容"）→ 按要求修改 doc.md → 修改完成后**再次请求确认**（循环直到用户确认）
2. **tasks.md 确认**（Step 4 完成后）：同上逻辑

### 豁免条件

以下情况**跳过所有用户确认**，直接完成流程：
- 用户初始请求中包含"仅生成方案"、"只出方案"、"不需要后续实现"、"不需要任务拆分"、"只要方案文档"等仅生成文档意图
- 用户选择了**文档模式**

### 确认阻断规则

- 确认步骤是**强制性的**，不可跳过、不可自动跳过
- 未收到用户明确同意前，禁止执行 Step 5（代码实现）及之后的任何步骤
- 确认请求必须明确告知用户下一步是什么（如"确认后将进入任务拆分"或"确认后将开始代码实现"）

# 完整模式详细步骤

## Step 1：需求理解与信息收集

### 1.1 需求文档获取

执行信息收集前，先检查用户是否已提供需求文档，并按以下规则获取内容：

| 输入类型 | 处理方式 |
|---------|---------|
| 用户直接粘贴的文档文本 | 直接使用 |
| 本地文件路径 | 使用 `read_file` 读取 |
| 知识库链接（`ku.baidu-int.com/knowledge/...`） | 通过 `ku-doc-manage` skill 获取文档内容：先用 `skill` 工具加载 `ku-doc-manage`，再调用其 `KuApiClient.query_content(url=...)` 方法，传入完整知识库 URL 获取结构化内容 |
| 以上均未提供 | 跳过文档获取，在下方信息确认项中向用户索取 |

> **禁止使用 WebFetch 或 playwright 访问知识库链接**，必须通过 `ku-doc-manage` skill 获取，以保证文档结构的完整性。

### 1.2 基础信息收集

一次性向用户展示**启动设计所必需的基础信息**，让用户在一条消息中补充，避免多轮对话：

```
请确认以下信息（已有的直接填写，没有的写"无"）：

1. 需求背景 & 目标收益：MRD/文档链接、功能范围
2. 涉及模块：前端/后端/数据？跨服务联动？
```

> **注意**：
> - 方案文件名（`.comate/specs/{feature_name}/`）从需求标题自动推导，无需询问用户。
> - 技术约束（性能指标、可用性目标）和技术栈（存储选型、框架版本）等信息，如果用户未主动提供，不要在此时追问，留到 Step 2 代码探索后根据实际情况按需澄清（见 Step 2.2）。

---

## Step 2：探索代码库与澄清技术不确定性

### 2.1 代码探索

#### 2.1.1 模块识别

根据 Step 1 收集的需求信息，识别需要探索的代码模块：

| 场景 | 判断依据 | 探索策略 |
|------|---------|---------|
| **单模块** | 需求仅涉及 1 个服务/仓库内的少量文件 | 2.1.2 单模块探索 |
| **多模块** | 需求涉及多个服务、跨服务联动、或多个独立模块 | 2.1.3 多模块子 Agent 探索 |

> **判断提示**：当用户提到"跨服务"、"联动"、"XX 服务和 YY 服务"、"前端+后端"等关键词，或涉及模块数量 ≥ 3 时，应优先使用多模块探索策略。

#### 2.1.2 单模块探索

**用户提供了具体路径**：根据路径类型选工具

| 路径类型 | 示例 | 使用工具 |
|---------|------|---------|
| 单个文件 | `internal/service/user.go` | `read_file` |
| 目录 | `api/handler/` | `list_dir` + `read_file` |
| 通配符路径 | `internal/service/*.go`、`**/*_repo.go` | `glob_path` + `read_file` |

**用户未提供路径**：使用 Explore Agent 分析与需求相关的模块结构、数据模型、接口定义。

**Explore Agent 使用规范**（单模块场景）：

| 场景 | 推荐工具 | 禁止 |
|------|---------|------|
| 读已知路径的文件 | `read_file` | Explore |
| 搜索函数名、常量、接口路径 | `grep_content` | Explore |
| 按文件名模式查找 | `glob_path` | Explore |
| 理解某段逻辑属于哪个模块 | `Explore`（单问题） | 多任务批量 |
| 理解某功能的整体调用链 | `Explore`（单问题） | 多任务批量 |

- 每次 `delegate_subtask(Explore)` 只包含 **1 个明确问题**
- 问题必须是语义性的（"X 功能在哪里实现？"），而非路径性的（"读取 A/B/C.go"）

#### 2.1.3 多模块子 Agent 探索

当需求涉及多个模块时，**必须将每个模块的探索任务委托给独立的 Explore 子 Agent**，避免主 Agent 上下文被大量代码填满。

**执行步骤**：

1. **拆分探索任务**：将需求拆解为 N 个独立的模块探索任务，每个任务聚焦一个模块/服务/代码区域
2. **并行派发**：在**同一条消息中**发起多个 `delegate_subtask(agent_type=Explore)` 调用，每个 Agent 负责一个模块
3. **精确化查询**：子 Agent 的查询必须**按需裁剪**，只请求与当前需求直接相关的信息段，禁止使用"全量摘要"模板。

**可选信息段（仅选取需要的段）**：

| 信息段 | 何时需要 | 模板片段 |
|--------|---------|---------|
| 分层结构 | 首次接触该模块 | `- 分层结构：列出关键目录及职责（一行一条，不含代码）` |
| 数据模型 | 需求涉及该模块的 DB 表 | `- 与 [需求关键词] 相关的表结构：表名、核心字段摘要（禁止贴完整 DDL）` |
| 接口清单 | 需求涉及该模块的 API | `- 与 [需求关键词] 相关的接口：方法/路径/功能（仅列相关接口，非全量）` |
| 编码规范 | 需要在该模块新增代码 | `- 编码规范：命名约定、错误处理模式（从代码中推断，2-3 条即可）` |
| 调用链路 | 需求涉及跨模块交互 | `- 与 [需求关键词] 相关的上下游调用关系` |
| 缓存用法 | 需求涉及缓存 | `- 现有缓存：Key 模式、TTL、数据结构` |

**查询组装规则**：

1. 每个子 Agent 查询 **只包含与需求相关的 2-4 个信息段**，不得全选
2. 查询中必须包含 **需求关键词**（如"服务质量评价"、"订单取消"），让子 Agent 聚焦
3. 明确要求子 Agent **只返回与需求关键词相关的条目**，不要全量列举

**查询模板**：

```
请探索 [模块名称/目录路径]，聚焦与 [需求关键词] 相关的部分，按以下格式返回：

## 模块概述
- 职责：[一句话]
- 技术栈：[框架、存储、中间件]

[从上表中选取 2-4 个信息段拼接在此]

注意：只返回与 [需求关键词] 直接相关的内容，无关的表/接口/文件不要列出。
```

**反模式示例**：

- ❌ "请探索 inspectcenter 的完整代码结构，列出所有表、所有接口、所有编码规范"
- ✅ "请探索 inspectcenter，聚焦与**服务质量评价**相关的部分：(1) 分层结构 (2) 相关表结构 (3) 编码规范"
- ❌ "请探索 workstation-doctor-ui 的全部质检相关接口"
- ✅ "请探索 workstation-doctor-ui，聚焦**历史问诊列表**的调用链路和与评价展示相关的接口"

4. **结果聚合**：所有子 Agent 返回后，主 Agent 在**内部整合**为一份统一摘要，要点：
   - 提取各模块间的**依赖关系**和**调用链路**
   - 合并重复或交叉的信息（如多个模块引用同一数据模型）
   - **仅保留**与 doc.md 各章节直接相关的信息，丢弃探索过程中的中间细节
   - 聚合结果不超过 1500 字（约 750 tokens），超出时按 doc.md 章节优先级裁剪

> **Token 节约原则**：
> - 子 Agent 的查询指令不计入主 Agent Token；子 Agent 执行过程中的所有 `read_file`/`grep_content` 结果也独立消耗 Token，不回流到主 Agent
> - 主 Agent 仅收到子 Agent 的**最终文本返回**（即上述结构化摘要）
> - 禁止在子 Agent 查询中要求"返回完整代码"或"列出所有函数"，仅要求精简摘要
> - 如果某个模块的探索结果特别关键（如需要精确的函数签名），主 Agent 可在聚合后**按需**对特定文件发起单次 `read_file`，而非让子 Agent 返回全部代码

**项目级规约检查**：同时检查项目根目录下是否存在 `.comate/rules/` 目录，若存在则读取相关规约文件（此步骤由主 Agent 直接执行，无需委托子 Agent）。

探索结论用于：写入 doc.md §6.1 的"当前逻辑"，以及 tasks.md 中引用真实路径。

### 2.2 识别不确定性 & 向用户澄清

代码探索完成后，梳理影响设计决策的技术不确定点，按以下原则处理：

#### Agent 可以自主获取的信息（不要问用户）

| 信息类型 | 获取来源 |
|---------|---------|
| 现有系统的调用链路、数据流转、模块结构 | Step 2.1 代码探索 |
| 当前使用的框架版本、存储选型、依赖关系 | Step 2.1 代码探索（依赖管理文件、项目配置） |
| 当前错误处理、日志设计、监控指标的模式 | 代码中已有的实现（如 middleware、logger 初始化） |
| 数据库标准字段、索引设计原则 | `references/database-design-standard.md` |
| 缓存 Key 命名、TTL、一致性策略 | `references/cache-design-standard.md` + 代码中已有的缓存用法 |
| 数据校验规则、接口标准参数 | 代码中已有的校验逻辑和接口定义 |
| 安全防护措施（SQL 注入、XSS、鉴权） | doc.md §6.5 强制检查项，直接按标准补全 |

#### 必须向用户澄清的信息

以下信息**无法从代码、规范文件或项目配置中获取**，必须向用户确认：

- **未明确的业务规则**：如"数据删除是物理删除还是逻辑删除"、"并发冲突时是覆盖还是拒绝"、"状态流转是否有特殊约束"
- **设计意图与未来规划**：如"这个模块后续是否会有其他服务复用"、"数据量未来一年的增长预估"
- **外部依赖的约束**：如"对接的第三方系统是否有调用频率限制"、"上游服务的数据格式是否会变更"
- **非功能需求的具体量化指标**：如"目标 QPS 是多少"、"接口响应时间上限"、"数据一致性要求（强一致/最终一致）"
- **多种可行方案之间的取舍**：如"新建独立服务 vs 嵌入现有模块"、"同步调用 vs 异步消息"，当两种方案各有利弊且代码无法给出答案时
- **项目级规约未覆盖的盲点**：如规范文件中没有定义的特殊字段命名约定、团队内部约定俗成的开发规范

> **判断标准**：如果代码、规范文件、项目配置中能找到答案，就不要问。只有当以上三个来源都**无法提供**时，才向用户澄清。

#### 沟通原则

1. **每次只问 1-2 个问题**，按阻塞程度排序，最影响设计的先问
2. **问题要具体明确**，说明为什么需要这个信息以及对设计的影响
3. **提供多种信息来源方式**：文字说明、文档路径、代码路径均可
4. **用户提到的文档直接读取**，不要再问"我可以读这个文档吗？"
5. **探索中发现的信息缺口立即标记**，不要等到写方案时才发现缺信息

> **禁止基于局部代码片段推断完整机制**——拿不准的地方宁可停下来问一句，也不要带着错误假设往下写。

## Step 3：生成 doc.md（Phase 1 - 最终技术方案文档）

**必须先读取 `references/doc-template.md`**，以其为骨架和内容生成指南填充内容。doc-template.md 中的每个章节都包含生成提示和强制检查项，按其指引逐章节填写。

**规范文件延迟加载**：按以下时机逐个加载，不涉及的章节标记 `N/A: [原因]` 即可，对应规范文件**不要读取**：

| 写到哪个章节 | 此时加载 |
|-------------|---------|
| §6.2 数据结构 - 数据库部分 | `references/database-design-standard.md`（仅涉及 DB 时） |
| §6.2 数据结构 - 缓存部分 | `references/cache-design-standard.md`（仅涉及 Redis 时） |
| §6.4 接口设计 | `references/api-design-standard.md`（仅涉及接口时） |

### 写入方式

使用 `write_file` 将 doc.md 写入 `.comate/specs/{feature_name}/doc.md`。

### 用户确认

> 按"用户确认机制"执行。doc.md 写入后立即停止，输出确认请求，等待用户同意后进入 Step 4。

doc.md 末尾必须包含质量检查清单（来自 `references/doc-template.md` 末尾），并逐项标注 ✅/❌/N/A。不合格项（❌）必须修复后才能提交用户确认。

## Step 4：生成 tasks.md（Phase 2 - 代码实现任务）

用户确认 doc.md 后执行。读取 `references/tasks-template.md` 作为骨架，基于 doc.md 设计和 Step 2 探索结论填写：
- 所有路径占位符替换为真实文件路径
- 验证类任务标记 `⚠️ 人工确认`，不自动完成

### 任务拆分规则

- **数据层**：DDL 执行、数据访问逻辑、缓存逻辑 → 分别独立任务
- **业务层**：按 doc.md §6.1 架构图中的模块拆分
- **接口层**：按 doc.md §6.4 中的接口数量拆分（多接口可合并为一个任务）
- **验证类任务**：标记 `⚠️ 人工确认`，不自动标记完成
- **路径精确**：所有路径占位符必须替换为 Step 2 探索到的实际文件路径
- **任务数量**：按实际需求确定，不硬编码固定数量

### 写入方式

使用 `write_file` 将 tasks.md 写入 `.comate/specs/{feature_name}/tasks.md`。

### 用户确认

> 按"用户确认机制"执行。tasks.md 写入后立即停止，输出确认请求，等待用户同意后进入 Step 5。

---

## Step 5：执行代码实现（Phase 3）

用户确认 tasks.md 后，逐任务执行：

1. 按 tasks.md 中的任务顺序执行
2. 每完成一个 Task，立即更新 tasks.md 中对应的 `[ ]` → `[x]`
3. **验证类任务**（标记 `⚠️ 人工确认`）不自动标记完成，等待用户确认
4. 代码实现必须符合 doc.md 中的设计（DDL 字段、缓存 Key、接口格式、错误码）

---

## Step 6：生成 changes.md（Phase 4）

读取 `references/changes-template.md` 作为骨架，记录代码实现过程中所有文件变更（新增/修改/删除），含变更摘要和说明。

使用 `write_file` 写入 `.comate/specs/{feature_name}/changes.md`。
