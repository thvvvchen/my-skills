# 缓存设计通用规范

> 本文件为通用规范，项目级规约（scenarios/redis.mdr）优先级更高，两者同时加载时以项目级为准。

## 1. 基本原则

- **[强制]** 所有 Key 必须设置 TTL，严禁无过期时间的 Key（缓存仅作为加速层，不做永久存储）
- **[强制]** 所有操作必须传递 `context.Context`
- **[强制]** 必须处理缓存操作错误，区分"Key 不存在"和"服务错误"
- **[推荐]** 大 Value 考虑压缩或拆分

## 2. Key 命名规范

### 2.1 命名格式【强制】

```
{业务系统前缀}:{模块}:{业务含义}:{标识ID}
```

示例：
- `health-mcp:article:views:{article_id}`
- `health-mcp:user:session:{user_id}`

### 2.2 命名原则

| 原则 | 说明 |
|-----|------|
| 表意清晰 | Key 名必须清晰反映所存数据的内容与用途 |
| 统一前缀 | 同模块数据采用统一前缀，利于区分数据归属 |
| 字符规范 | 统一使用小写字母、数字及分隔符 `:` `-`，禁止空格和特殊字符 |
| 预留扩展 | Key 名简洁但预留扩展空间，避免后续改名破坏整体规则 |

## 3. 数据结构选型

| 数据结构 | 适用场景 | 示例 |
|---------|---------|------|
| **String** | 计数器、简单 KV、开关、分布式锁 | `article:views:{id}` + `INCR` |
| **Hash** | 对象属性缓存（字段可单独读写） | `user:{id}` 存储多个属性字段 |
| **List** | 最新动态、简单消息队列 | `user:news:{id}` + `LPUSH`/`LRANGE` |
| **Set** | 去重集合、关系管理 | `article:tags:{id}` + `SADD`/`SMEMBERS` |
| **Sorted Set** | 排行榜、优先级队列、时间线 | `rank:views:daily` + `ZADD`/`ZRANGE` |

选型时需在方案中说明理由。

## 4. TTL 策略

| 数据类型 | 推荐 TTL | 说明 |
|---------|---------|------|
| 用户会话 | 30 分钟 ～ 2 小时 | 按业务需要调整 |
| 热点列表 | 5 ～ 30 分钟 | 高频更新数据不宜过长 |
| 静态配置 | 1 ～ 24 小时 | 变更频率低可适当延长 |
| 空值缓存 | 1 ～ 5 分钟 | 防止缓存穿透，不宜过长 |

- **[推荐]** 设置 TTL 时加入随机偏移量，防止缓存雪崩
  ```
  实际 TTL = 基础 TTL + random(0, 基础TTL * 10%)
  ```

## 5. 缓存一致性策略

### 5.1 写入/更新时
- **推荐策略**：先更新数据库，再删除（而非更新）缓存
- 对一致性要求高的场景，考虑使用分布式锁保护回源逻辑

### 5.2 三大缓存问题应对

| 问题 | 描述 | 应对方案 |
|-----|------|---------|
| **缓存穿透** | 查询不存在的数据，每次都打到 DB | 缓存空值（短 TTL）；布隆过滤器 |
| **缓存击穿** | 热点 Key 过期，大量请求同时回源 | 分布式锁控制，仅一个请求回源 |
| **缓存雪崩** | 大量 Key 同时过期，DB 压力骤增 | TTL 加随机偏移；多级缓存 |

## 6. 操作规范

### 6.1 批量操作
- **[推荐]** 多个无关 Redis 操作优先使用 Pipeline 合并发送，减少网络往返
- **[推荐]** 批量操作分批执行，每批不超过 100 条，避免阻塞 Redis 线程

### 6.2 原子性
- 需要保证原子性的操作，使用事务（`MULTI`/`EXEC`）或 Lua 脚本

### 6.3 错误处理
- `Key 不存在`（redis.Nil）：缓存未命中，回源数据库后回填，**不需要重试**
- 服务错误：排查 Redis 服务故障，按需重试或降级
