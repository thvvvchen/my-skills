# 技术方案生成

生成可落地的技术方案，并在需要时将方案转化为可执行的代码任务与实施记录。优先复用项目现有架构、约定和代码模式。

## 选择模式

根据请求选择一种模式；无法判断时，先询问用户。

- **完整模式**：需求理解、代码探索、`doc.md`、`tasks.md`、实现、`changes.md`、`summary.md`。
- **增量模式**：用户给出已有方案，先分析缺口，再补充方案并只为新增部分拆分和实施任务。读取 `references/workflow-incremental.md`。
- **仅文档模式**：用户明确只需要方案、无需实现或任务拆分。完成 `doc.md` 后结束。

将产物写入 `{PROJECT_ROOT}/.comate/specs/{feature-name}/`。从需求标题推导小写连字符形式的 `feature-name`；目录不存在时创建。

## 按需读取参考资料

始终先读取 `references/workflow.md` 中当前步骤对应的内容，不要预读全部资料。按下列时机加载：

- 编写方案：`references/doc-template.md`。
- 涉及数据库、缓存或接口：分别读取 `database-design-standard.md`、`cache-design-standard.md`、`api-design-standard.md`。
- 编写任务、变更和总结：分别读取 `tasks-template.md`、`changes-template.md`、`summary-template.md`。
- 增量补丁：读取 `patch-template.md`。

## 收集与探索

1. 收集需求背景、目标、范围、涉及模块和已有需求文档。对本地路径直接读取；对 `ku.baidu-int.com` 链接使用 `ku-doc-manage`，不要使用网页抓取工具。
2. 探索相关代码、配置与依赖，识别真实文件路径、调用链、数据模型、接口和既有编码模式。检查项目级规则（例如 `.comate/rules/`）并优先遵守。
3. 多模块或跨服务需求时，为每个独立模块并行进行聚焦探索；每项只收集与需求直接相关的信息，合并为简洁结论。
4. 仅对无法从需求、代码、配置和规则中确定、且会影响设计决策的业务规则或取舍向用户澄清；每次询问 1-2 个问题。

## 编写方案

以 `doc-template.md` 为完整骨架填充 `doc.md`，不得删除章节。必填章节必须有实质内容；不适用的可选章节写 `N/A: 原因`。

- 给出架构、流程和依赖关系时优先使用 Mermaid。
- 每个代码片段注明相对项目根目录的来源文件；变更描述精确到文件、函数、字段或接口，避免“修改相关逻辑”等模糊表述。
- 涉及数据库、缓存、接口时满足对应标准：DDL、索引和数据量评估；缓存 Key、TTL、一致性和三类风险；接口鉴权、参数、统一响应、错误码与幂等性。
- 覆盖安全、性能、监控、日志、发布回滚和风险应对。完成后按模板中的质量清单逐项自检并修复不合格项。

## 确认与实施

完整模式和增量模式必须遵守以下确认闸门：

1. 写入 `doc.md` 后停止，向用户请求确认。用户要求修改时更新方案并再次请求确认。
2. 获得确认后，以 `tasks-template.md` 为骨架生成 `tasks.md`。每项必须指向真实模块/文件，描述可执行的改动和验证方式。
3. 写入 `tasks.md` 后再次停止并请求确认。未确认前不得实现代码或生成后续记录。
4. 确认后按任务顺序实施；每完成一项立即将其标记为完成。标为人工确认的任务仅在用户确认后完成。
5. 使用模板生成 `changes.md`，记录新增、修改、删除的文件和行为；生成 `summary.md`，汇总任务状态、验证结果、风险和待办。

## 验证

在交付前确认：所有产物位于目标目录；方案章节完整；任务引用真实路径；代码变更与方案一致；已运行适用的构建、测试、静态检查或明确记录无法运行的原因。
