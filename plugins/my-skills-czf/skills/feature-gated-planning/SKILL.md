# 功能关卡规划

## Workflow

1. 用一句话复述目标，列出已知的输入、输出、约束、验收标准和未决问题。缺少会显著改变方案的信息时，先向用户确认。
2. 阅读与需求相关的代码、文档和测试，识别现有边界、相似实现、可复用组件及不可变更的约束；不要根据示例项目假定语言、框架或分层方式。
3. 按用户可感知的业务能力拆分任务。每个任务必须交付一项可独立验证的完整功能，包含该项目实际需要的数据、领域或服务、接口或界面、错误处理和自动化测试。
4. 拒绝两类拆分：覆盖整个系统的大任务，以及只改一个技术层的碎片任务。若功能之间存在依赖，明确前置任务、阻塞条件与可并行部分。
5. 为每个任务写明目标、涉及文件、实现步骤、测试策略、验证命令、预期结果和完成标准。采用项目已有的测试、格式化、静态检查和提交规范；没有证据时标为待确认，不要编造命令、路径或代码。
6. 按测试先行组织实施步骤：先定义失败的行为验证，再实现最小改动使其通过，最后进行必要的重构与完整验证。对无法进行 TDD 的改动，说明原因和替代验证方式。
7. 在每个功能任务末尾设置人工确认关卡。关卡应汇总已交付能力、验证证据、遗留风险和下一任务预览，并明确要求用户选择继续、调整、重排或暂停。
8. 计划完成后检查：每项工作都对应业务能力和验收标准；依赖关系无环且可执行；测试覆盖主路径、失败路径与关键边界；后续任务不会在未经确认时自动开始。

## 输出格式

按以下结构输出计划，并根据项目实际情况增删层次：

```markdown
# [模块或能力]实施计划

**目标**：[一段话说明交付结果]
**范围与约束**：[明确包含、不包含和待确认事项]
**总体方案**：[技术路径与关键取舍]

## 任务 1：[完整功能名称]

**能力**：[用户或调用方获得什么]
**依赖**：[前置任务或无]
**涉及内容**：[文件、模块或接口]

1. [先写的验证或测试]
2. [最小实现]
3. [错误处理、迁移或兼容性工作]
4. [格式化、静态检查、集成验证]

**验收标准**：
- [可观察、可验证的结果]

**验证**：
- `[项目中实际存在的命令]`，预期：[结果]

### 人工确认关卡

已完成：[能力与证据]
风险或待定：[事项]
下一项：[任务 2 概览]

等待用户明确选择：继续、调整当前任务、调整后续计划，或暂停。
```

## 约束

- 以功能完整性为边界，不强制 DAO、Service、API 等特定架构层次。
- 不把计划中的示例代码、文件路径、技术栈或提交命令伪装成项目事实。
- 未获得人工确认时，只可讨论或修订下一任务，不得开始实施下一项功能。
