# 精简代码审查

## 核心原则

审查结论必须能回指到具体变更、调用链或可复现证据。优先报告会造成错误行为、数据损坏、安全风险、兼容性回退或明显缺少验证的问题；不要把个人偏好当成缺陷。

## 执行流程

1. **固定范围**
   - 用户指定 commit/PR/diff 时，直接以它为范围；支持一个或多个 commit。
   - 未指定时，优先使用 CI/PR 提供的变更信息，其次选择最新 commit。
   - 先取得稳定的 `BASE`、`HEAD`、完整 diff 和变更文件清单，再开始分析。后续历史上下文必须基于 `HEAD`，不能用当前工作树快照替代。

2. **识别技术上下文**
   - 根据变更路径读取必要的项目配置，如 `package.json`、`go.mod`、`pom.xml` 或 `build.gradle`。
   - 只加载命中的框架、语言和项目规则；没有命中特定规则时使用通用审查标准。

3. **高层审查**
   - 先画出受影响的入口、核心逻辑、状态/数据写入、异步边界和清理路径。
   - 检查变更是否破坏不变量、错误处理、权限边界、兼容性、性能上限或生命周期。
   - 对无法从 diff 确认的链路标记“需要上下文”，不要猜测结论。

4. **逐文件审查**
   - 覆盖变更清单中的每个文件；按 `P0`、`P1`、`P2`、`P3` 排序。
   - 对高风险候选再读取调用方、被调用方、类型定义、测试和配置，确认问题真实存在。
   - 复用已有测试、静态检查或最小复现验证 `P0/P1`；没有运行验证时明确写出未验证。

5. **输出结论**
   - 只输出已确认或证据充分的问题；每条包含：级别、文件/行号、问题、影响、修复建议、验证信号。
   - 没有问题时明确写“未发现可确认缺陷”，并列出剩余测试缺口和审查范围。

## 风险优先级

| 级别 | 判定 |
|---|---|
| P0 | 阻断发布、数据丢失、严重安全问题或大范围不可用 |
| P1 | 高概率错误、核心流程回归、关键兼容性/可靠性问题 |
| P2 | 一般功能缺陷、边界条件、可维护性或性能风险 |
| P3 | 低风险改进，只有在能明确提升质量时提出 |

## 必查维度

- 正确性：输入边界、空值、错误分支、状态不变量。
- 数据与并发：竞态、重复请求、乱序回包、事务/幂等、资源上限。
- 生命周期：定时器、订阅、监听器、连接、缓存和组件销毁后的清理。
- 安全与兼容：权限、敏感数据、注入、协议/版本兼容和回滚路径。
- 验证：新增行为是否有合适测试；测试是否覆盖失败和边界场景。

## 输出模板

```text
审查范围：<BASE>..<HEAD>

发现：
- [P1] path/to/file.ts:42
  问题：<具体可复现的问题>
  影响：<用户、数据或系统影响>
  建议：<最小修复方向>
  依据：<调用链、测试结果或命令>

结论：<可合并 / 需修复 / 阻断>
未验证项：<未运行的测试、依赖的外部上下文>
```

## 常见误区

- 未固定 `BASE/HEAD` 就开始看工作树。
- 只看改动行，不追调用方、错误路径和清理路径。
- 把格式化、命名偏好或“看起来不优雅”当作缺陷。
- 没有运行验证却声称问题已确认或测试已通过。
- 用一条模糊建议替代文件、行号、影响和证据。
