# my-skills-czf : 技术项目面试总结

## 输入与事实核验

1. 先读取用户提供的文档、代码、变更记录或数据，提取项目目标、约束、关键文件、技术决策和验证证据。
2. 区分已实现、已验证、计划优化和推测内容；没有证据的线上指标不得写成既成事实。
3. 对缺少的关键信息使用“未提供”标记，并给出可补充的验证方式，不要用泛化术语填空。

## 固定输出层级

按以下顺序输出；没有内容的部分要说明缺失原因，不要保留空标题。

### 1. 简历写法

用一到两句话概括“负责什么 + 解决什么问题 + 采用什么关键技术 + 已确认的结果”。突出个人职责和可验证的技术动作，避免把团队工作全部写成个人贡献。

### 2. 面试表达结构

将内容组织为一段可口述的主线：业务场景与问题 -> 约束和风险 -> 方案对比 -> 最终选择及原因 -> 实现机制 -> 验证结果。优先解释关键取舍，而不是罗列 API 名称。

### 3. 背景

说明用户或业务场景、现有页面/系统结构、触发变化的条件、原方案的具体问题，以及本次改造的目标和边界。

### 4. 方案对比

列出两个到三个真实可行方案。每个方案都写清优点、缺点和适用条件，最后说明为什么当前场景选择最终方案。对比应围绕实际约束，例如动态布局、性能、交互、兼容性、维护成本或数据一致性。

### 5. 实际实现方案

按数据流或生命周期从底层到上层分步描述：输入和依赖、核心计算/状态、组件或模块边界、异常处理、事件与观察器、清理逻辑、平台差异和关键代码位置。涉及坐标、状态或并发时，明确坐标系、更新时机和释放条件。

### 6. 实现结果

先列出用户可观察的行为和已完成的验证，再单独列出有真实来源的量化指标。没有线上指标时，明确写“当前未采集”，并建议后续采集视觉回归通过率、性能、错误率或交互成功率等合适指标。

### 7. 优化复盘

指出当前实现仍可能存在的重复计算、依赖不稳定、生命周期风险、测试缺口或抽象机会。每条优化都要说明收益、代价和触发条件，区分立即可做项与后续项。

### 8. 面试追问与准备要点

从最终方案和取舍中生成五到八个高概率追问，并为每个问题准备简洁、可追溯的回答。至少覆盖：为什么不用其他方案、关键 API 或机制为什么这样选、边界场景、性能、清理/内存安全、如何验证有效性，以及未采集指标如何补齐。

## 表达约束

- 使用中文和清晰的小标题；面试表达要能直接口述，代码细节放在实现方案中。
- 只总结真实输入中的事实，不虚构性能数字、线上结果、用户反馈或个人职责。
- 同时保留“选择了什么”和“为什么选择”，避免只写技术名词。
- 对方案、实现和结果建立一一对应关系；结果必须能回指实现动作或验证记录。
- 用户未要求其他格式时，使用上述八级结构，不额外加入营销式总结。
